# ScreenX — Technical Status Report & Development Roadmap

**Product:** ScreenX (repository: `Rust-Screenx-HR-Automatization`)
**Period covered by the roadmap:** October 2025 – April 2026
**Report date:** September 2026
**Prepared from:** git history, database migration timeline, source tree, and existing project documentation (`architecture.md`, `README.md`, `API_DOCUMENTATION.md`, `ONEF_INTEGRATION.md`, `DEPLOYMENT.md`)

---

## 1. Executive Summary

ScreenX is a recruitment-automation platform that bridges three systems: the **"Первая Форма" (OneF / 1F)** HR/ERP system used internally by the business, a **Telegram bot + Mini App** used by candidates, and **OpenAI-backed AI tooling** used to generate tests, grade answers, score CVs, and (most recently) digitize handwritten interview sheets.

Between **October 2025 and April 2026**, the platform was built from an empty schema to a working end-to-end pipeline: vacancy management → candidate registration/application → AI-generated or presentation-based testing → automated + AI grading → status tracking → bidirectional Telegram messaging → a first OneF synchronization layer, with anti-cheat protections and data-export tooling layered on before an April hardening pass. That six-month window is reconstructed below from the two most reliable timestamped sources in the repo: **migration filenames** (which predate git by three months) and **git commit history** (which begins January 27, 2026).

Since April 2026 the platform has continued to grow (admin authentication, OpenAI-only consolidation, AI-driven candidate-to-vacancy matching, handwritten form OCR — see §4), and Section 2 below describes the platform **as it stands today**, not just as of April 2026.

## 2. Current Condition of the Platform (as of September 2026)

### 2.1 What ScreenX does

Core flow: HR creates vacancies and AI-generated or presentation-style tests → candidates register/apply via a Telegram Mini App → candidates take a proctored online test → answers are graded (auto-graded MCQ + AI-graded open answers) → CVs are scored for suitability against the vacancy by AI → results, grades, and status changes are pushed back into OneF → HR and candidates exchange messages over a Telegram bridge that is mirrored into OneF's own inbox. OneF also now gets an AI-generated ranking of a candidate against its full vacancy catalogue, and can send photographed, handwritten interview-evaluation sheets to be transcribed into structured text.

### 2.2 Architecture & technology stack

| Layer | Technology |
|---|---|
| Backend | Rust, **Axum 0.7**, **SQLx 0.7** (Postgres driver, `runtime-tokio-rustls`), **Tokio** (full) |
| Database | PostgreSQL 15+ |
| Auth (admin panel only) | `jsonwebtoken` 9 (HS256), `argon2` 0.5 (argon2id password hashing), `subtle` (constant-time secret comparison) |
| HTTP client (outbound) | `reqwest` 0.11 (rustls) |
| Frontend | **Next.js 16.1.6** (App Router), **React 19.2**, Tailwind CSS 4, shadcn/ui on Radix primitives, TanStack React Query 5.90 |
| Frontend exports | `docx` 9.7 (Word), `exceljs` 4.4 (Excel), `recharts` 3.7 (dashboard charts) |
| AI | OpenAI API only — `gpt-4o` (chat + vision), `text-embedding-3-small` (embeddings) |
| Messaging | Telegram Bot API (webhook-driven) |
| External job portal | `job.koinotinav.tj` — read via REST, write via a Selenium/Chromedriver automation |
| Containerization | Docker + docker-compose (`backend`, `frontend`, `caddy`, `swagger-ui` services) |
| Edge / TLS | Managed upstream OpenResty (outside our control) terminates TLS for `dchr.koinotinav.com`; local Caddy serves plain HTTP on `:80` |

The repo is a two-part monorepo: `recruitment-backend/` (Rust service, entry `src/main.rs`, shared state in `src/lib.rs::AppState`) and `frontend/` (Next.js HR dashboard + public candidate pages, proxying `/api/*` and `/uploads/*` to the backend via Next rewrites).

|---|---|---|---|---|
| Base | `/health` | none | none | Readiness probe |

Roughly 60 distinct routes are registered in `main.rs` today, up from the ~20 documented in the original `README.md`.

### 2.4 Background workers (spawned at startup)

| Worker | Interval | Purpose |
|---|---|---|
| Telegram webhook manager | every 30 min | Keeps the bot's registered webhook URL in sync with `WEBAPP_URL` |
| AI job queue | ~750 ms poll | Processes `ai_jobs` (AI test generation) |
| Notification/webhook delivery | ~1 s poll | Delivers `webhook_logs` with exponential backoff (up to 3 attempts, capped at 3600 s) |
| Deadline checker | every 60 s | Flags test-attempt deadlines, sends warnings, marks `timeout`/`escaped` |
| OneF vacancy-catalogue sync | scheduled snapshot | Refreshes `onef_vacancies` from `getVacancies`, feeding the candidate-matching service |

### 2.5 External integrations

- **OneF / "Первая Форма"** — bidirectional. Outbound notifications fan out concurrently to **every** server in `ONEF_BASE_URLS` (a March 2026 hardening; legacy single `ONEF_WEBHOOK_URL` still supported as a fallback). Inbound partner API is documented in `ONEF_SWAGGER.yaml` / `ONEF_INTEGRATION.md`.
- **Koinotinav job board** — read-only listing via `koinotinav_service.rs`, tolerant of a messy upstream schema (HTML-tag stripping, flexible bool/int/string coercion).
- **Telegram** — bot + Mini App; candidate identity keyed by `telegram_id`.
- **External vacancy posting** — no write API exists on the job board, so `external_vacancy_service.rs` drives a Python/Selenium/Chromedriver script baked into the Docker image to create/delete listings; the payload includes the partner site's login credentials.

### 2.6 AI subsystem

All AI calls run through **OpenAI only** (consolidated 2026-06-24 from an earlier OpenAI/OpenRouter split): `gpt-4o` for test generation, vacancy-description generation, CV/candidate suitability scoring (including vision input), candidate-to-vacancy matching, and interview-form OCR transcription; `text-embedding-3-small` for embeddings. OpenAI 429s are retried rather than dropped (hardened 2026-08-24). Two pieces of AI infrastructure from the original October 2025 "AI quality infra" migration — an LLM-judge quality critique (`eval_service.rs`) and an embeddings service (`embed_service.rs`) — are fully implemented but have **no call sites anywhere in the codebase**; they were scaffolded and never wired into the generation pipeline.

### 2.7 Security & auth posture

JWT auth (`require_bearer_auth`, `require_hr_or_admin`, `require_admin`) exists in `middleware/auth.rs`, but **by explicit design it is only attached to `/api/auth/*`**. The business routers — `/api/integration/*`, `/api/public/*`, `/api/onef/*` — remain intentionally unauthenticated because OneF and other partners call them directly and adding a token requirement would break that integration. The only integrity check on the business surface is `X-Webhook-Secret` on `/webhook/*`. This is a known, accepted tradeoff, mitigated only at the network layer (backend not directly internet-exposed; sits behind Caddy/OpenResty inside a Docker network). CORS is `permissive()`. An admin login system (JWT, argon2id, brute-force lockout after 5 failed attempts/15 min) was added 2026-06-22 for the dashboard's own user management, seeded with a default admin account that is forced to rotate its password on first login.

### 2.8 Deployment & infrastructure

Production serves `https://dchr.koinotinav.com` from a server with no public IP; a managed upstream OpenResty box (outside this team's control) owns the public IP and TLS certificate and reverse-proxies plain HTTP to this server's Caddy on `:80`. Caddy must not attempt its own TLS/auto-redirect or it loops with OpenResty. `docker-compose.yml` runs `backend`, `frontend`, `caddy`, and `swagger-ui`. The backend runs `sqlx::migrate!` on every boot.

### 2.9 Testing & dev workflow

Five backend integration-test files cover grading, the integration API, the OneF API, the public API, and webhook delivery, plus a dedicated Python script (`tools/ocr_assets_test.py`) for exercising the OCR pipeline against reference images. There is no local Postgres on the primary dev machine: the backend builds with `SQLX_OFFLINE=true` against the checked-in `.sqlx` query cache and is verified against a disposable Docker Postgres. `.env` ships with placeholder secrets (including a dummy `OPENAI_API_KEY`), so AI-path testing locally exercises only the failure path unless a real key is supplied.

### 2.10 Known technical debt & open risks

| Item | Detail |
|---|---|
| Hard-coded OneF IPs | `notify_test_status` and `notify_new_message` in `onef_service.rs` still POST to a literal `192.168.1.47`, bypassing the configurable `ONEF_BASE_URLS` fan-out that every other OneF call site uses. Breaks silently if that IP ever changes. |
| No auth on business routes | Accepted tradeoff (§2.7), but worth re-flagging to stakeholders periodically, especially as the OneF-facing surface has grown (matching, OCR, messaging all unauthenticated). |
| Permissive CORS | `CorsLayer::permissive()` across the API. |
| Dormant AI-quality infra | `eval_service.rs` / `embed_service.rs` (LLM-judge + embeddings) have been unused since October 2025 — either finish wiring them in or remove them. |
| Selenium credential handling | External vacancy posting ships the partner site's email+password in the automation payload each call. |
| Duplicate log line | Minor: `onef_service.rs`'s success log for `notify_grade` prints twice. |

### Narrative summary

The first four months (Oct 2025 – Jan 2026) were pure build-out, in a fixed sequence: **AI scaffolding → vacancies → candidates → applications → assessment variety (presentations) → grading rigor (overtime handling, review status, AI rating)**. This is the shape of an MVP being assembled domain-by-domain before any external partner touches it. Putting the code under git on January 27 marks the point the project became a managed, collaborative codebase rather than a single-developer working tree.

February 2026 is where the platform stopped being a standalone tool and became **OneF-integrated**: the messaging bridge and the first `onef_sync` migration landed in the same week, alongside the anti-cheat system that made proctored testing viable for real candidates, and export tooling that let HR get data out. March–April 2026 was a deliberate hardening pass — the OneF fan-out rework and the written architecture audit both suggest a point where the team stepped back, documented what had been built, and fixed structural weak points (single-server dependency, description-generation bugs) before the next feature push.
